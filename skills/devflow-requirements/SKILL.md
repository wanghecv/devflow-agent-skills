# devflow 需求对话与澄清

## 定位
把"我想做个 XX"这种模糊想法，通过结构化提问收敛成一份可执行、可验收的需求结论纪要。这是黄金法则"先对话后执行"的落地点，也是整个项目最容易省钱的一步——需求阶段多问一句，开发阶段少返工一天。

## 何时使用
- 用户提出做软件但需求不清晰
- 新项目启动的第一步
- 二次开发前需要重新对齐范围
- 用户说"先聊聊""帮我理理需求"

## 产出物
一份《需求结论纪要》，作为 PRD 阶段的输入。

## 执行步骤

### 1. 用结构化提问打开话题（一次聚焦几个关键问题，不要一口气问 20 条）
优先用 AskUserQuestion 这类选择题工具降低用户回答成本。核心澄清维度：
- **目标与动机**：解决什么问题？给谁用？成功长什么样？
- **用户与角色**：有哪几类使用者？各自的核心诉求和权限差异？
- **核心场景**：最高频、最重要的 3~5 个使用场景是什么？
- **范围边界**：这一期做什么、明确不做什么（MVP 边界）？
- **约束**：技术栈是否已定？部署环境？合规/安全要求？时间/预算？
- **数据与集成**：需要对接哪些外部系统/数据源？
- **验收标准**：怎样算做完了？有无量化指标（性能/效率/容量）？

### 2. 追问与澄清技巧
- 对模糊表述用 5Why 追根因（"要个后台" → 后台给谁、管什么、为什么现在需要）。
- 对每个功能问"谁在什么情况下用它完成什么"，识别真实需求 vs 伪需求。
- 主动暴露假设："我理解你说的是 X，对吗？"让用户确认或纠正。
- 区分"必须有(Must)/应该有(Should)/可以有(Could)"，为范围取舍铺路。

### 3. 收敛成结论纪要（结构化落盘）
纪要应包含：项目一句话定义、目标与非目标、用户角色清单、核心场景清单、MVP 范围边界、已知约束（技术/环境/合规/时间）、外部集成、验收标准与量化指标、未决问题（用 XXX 或"待确认"标注）。

### 4. 确认闭环
把纪要复述给用户确认，达成一致后再进入 PRD 阶段。有分歧当场解决，不带疑问往下走。

## 交接
- → devflow-prd：纪要直接展开为正式 PRD。
- → devflow-product-definition：角色与场景是功能矩阵的输入。
- → devflow-tech-stack：约束条件（是否已定技术栈、部署环境）决定选型空间。

## 关键陷阱
- 一次抛太多问题，用户疲劳 → 分批、用选择题。
- 用户说什么就记什么，不追根因 → 伪需求进开发。
- 不敢暴露假设，闷头理解错 → 复述确认。
- 范围不划边界 → 需求无限膨胀，永远做不完。
- 未决问题不留痕 → 后面各自臆测，产生分歧。

## 验证
- 纪要覆盖上述全部维度，无遗漏。
- 用户已明确确认纪要内容。
- 未决项都被标注，没有隐藏假设。
