# devflow 部署与运维

## 定位
把开发成果稳定地发布到运行环境并持续维护。部署的核心纪律是：**流程可重复、环境可复现、变更可回滚、故障可定位**。本 skill 提供通用部署方法论，具体平台/命令由项目环境决定并记入《项目事实文件》。

## 何时使用
- 代码改完要上线
- 首次部署或换环境
- 部署后无变化/构建报错排查
- schema 或配置变更后的发布

## 产出物
部署流程说明、部署脚本、运行配置、故障速查表。

## 执行步骤

### 1. 明确部署模式（按项目约定）
先确认本项目的部署方式并记录：
- 构建在哪做（本地/CI/服务器）？发布靠什么（拉取/推送/上传/镜像）？
- 运行靠什么托管（进程管理器如 PM2/systemd、容器如 Docker、Serverless、PaaS）？
- 环境事实：路径、端口、运行时版本、域名、依赖服务。
> 例：某类项目的模式是"本地只改源码不构建 → FTP 增量上传 → 服务器上 install+build → 进程管理器重启"。不同项目模式不同，务必先对齐，别套用。

### 2. 标准部署流程（通用骨架）
1. 准备：确认运行时版本、加载环境变量/配置。
2. 安装依赖（在正确的环境执行，注意镜像源/网络）。
3. **数据库变更**（若有 schema 改动）：先生成类型/客户端 → 再迁移/建表 → 顺序不能反（详见 devflow-database 变更 SOP）。
4. 构建产物。
5. 发布/重启服务。
6. 验证：健康检查 + 冒烟（devflow-testing）。

### 3. 环境与配置管理
- 环境变量/密钥与代码分离，绝不硬编码、绝不提交进版本库。
- 区分 dev/staging/prod 配置，用环境变量或配置中心注入。
- 运行时版本固定（如 Node/Python 版本），避免"本地能跑线上不行"。

### 4. 关键红线（部署最常见坑）
- **改了代码只重启不重新构建 → 改动不生效**。重启只加载旧构建产物，必须先构建再重启。
- **构建命令/标志要对**：用项目规定的构建方式，别凭记忆（特殊环境可能需要特定标志或禁用某些工具链）。
- **schema 变更顺序**：先生成/迁移再构建部署，否则新模型构建期报类型错。
- **数据库迁移必须含建表步骤**：只生成类型不建表 → 运行报"表不存在"。
- **依赖安装在目标环境做**：本地环境特殊（如外置磁盘）可能导致安装失败，按项目约定在服务器/CI 执行。

### 5. 进程/容器托管
- 配置进程管理（进程名、端口、host、实例数、自动重启、内存上限重启）或容器编排。
- 单实例 vs 多实例：涉及会话/内存状态时注意一致性。

### 6. 回滚与发布安全
- 每次发布前可回滚：保留上一版产物/镜像、数据库变更前备份。
- 破坏性变更分步、可逆；高风险发布考虑灰度/蓝绿。
- 发布后看日志与健康检查确认成功。

### 7. 运维排查
- 看日志（进程管理器日志/容器日志/应用日志）定位问题。
- 资源监控：CPU/内存/连接/端口占用。
- 数据库排查用项目可用的客户端/脚本（注意某些命令行工具对查询不回显结果，需用应用层脚本）。

## 交接
- → devflow-testing：部署后跑冒烟放行。
- 上游依赖 devflow-tech-stack（构建/运行约定）、devflow-database（变更顺序）。

## 关键陷阱
- 只重启不构建 → 改动不生效。
- schema 改了没先迁移/生成 → 构建类型错或运行报表不存在。
- 密钥硬编码/配置进版本库 → 泄露。
- 无回滚预案 → 发布出事无法快速恢复。
- 凭记忆用错构建命令/标志 → 构建失败。

## 验证
- 构建成功产出、服务进程/容器在线。
- 访问目标地址看到最新改动；健康检查通过；冒烟通过。
- 配置与密钥来自环境注入，未硬编码；回滚预案就绪。
