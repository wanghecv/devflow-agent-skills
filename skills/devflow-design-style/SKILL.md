# devflow 设计风格与美术规范

## 定位
把原型的"结构"赋予统一的"外观"。设计风格的本质是一套**可复用的约束（design token）**：颜色、字号、间距、圆角、阴影、图标、组件态。定了 token，全站视觉才一致，多个开发者/AI 才不会各写各的样式。

## 何时使用
- 原型确定后要定视觉语言
- 建立或统一设计系统
- 组件样式需要对齐规范

## 产出物
一份《设计规范 / Design Token 文档》，含色板、字体、间距、圆角、阴影、图标、组件样式、响应式与暗色模式约定。

## 执行步骤

### 1. 确立设计基调
- 产品气质：专业工具 / 消费级 / 数据密集 / 品牌导向？据此定风格（克制中性 vs 活泼鲜明）。
- 参考基线：若有品牌规范或参考产品，先提取其设计系统（可用 ui-designer skill 从截图提取）。

### 2. 定义 Design Token（核心）
- **色彩**：主色（品牌/操作）、中性色（背景/边框/文本灰阶）、语义色（成功绿/警告琥珀/危险红/信息蓝）。每种给出具体色值与使用场景。
- **字体**：字体族、字号阶梯（如 12/14/16/20/24/32）、字重、行高。
- **间距**：统一的 spacing scale（如 4 的倍数 4/8/12/16/24/32）。
- **圆角**：卡片/按钮/输入的圆角档位。
- **阴影/层级**：elevation 分级。
- **图标**：统一图标库与尺寸档位，禁止混用多套图标。

### 3. 组件样式规范
- 为常用组件（按钮、输入、卡片、表格、标签/徽章、弹窗、导航、空/加载/错误态）定义外观与交互态（默认/hover/active/disabled/focus）。
- 明确组件的 token 引用，不写死具体数值。

### 4. 响应式与可访问性
- 断点策略、移动/桌面布局差异（如桌面侧边栏、移动底部导航）。
- 对比度达标（WCAG AA）、焦点可见、可点击区域足够大。
- 暗色模式（若需要）：定义暗色 token 映射。

### 5. 落地方式
- 把 token 落到具体技术实现（CSS 变量 / Tailwind theme / 设计系统文件），供前端阶段直接引用。
- token 的具体值记入《项目事实文件》，设计规范本身讲方法。

## 交接
- → devflow-frontend-dev：前端严格引用本阶段 token，禁止自造样式。
- 上游依赖 devflow-prototype 的页面结构。

## 关键陷阱
- 不定 token 直接写样式 → 全站色值/间距五花八门，难统一。
- 混用多套图标库 → 视觉割裂。
- 组件不覆盖 hover/disabled/focus/空/错态 → 交互残缺、可访问性差。
- 忽略对比度与可点击区域 → 可用性差。
- token 值硬编码在组件里 → 改主题时全局返工。

## 验证
- 色彩/字体/间距/圆角/阴影/图标六类 token 齐全且有明确用途。
- 常用组件都有样式与完整交互态定义。
- 响应式断点与可访问性（对比度/焦点）有约定。
- token 已可被前端直接引用。
