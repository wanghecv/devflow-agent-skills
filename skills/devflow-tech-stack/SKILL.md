# devflow 技术栈选型与版本锁定

## 定位
技术选型不是追新，而是**在约束下做最省心的选择**。本阶段根据项目类型、团队能力、约束条件选出合适的技术栈，并把版本精确锁定、把踩坑点写成红线，让后续任何接手者（含 AI）不重复踩版本坑。

## 何时使用
- 新项目搭建前确定技术栈
- 二次开发前对齐现有栈
- 升级依赖前评估影响

## 产出物
《技术栈与依赖清单》：选型理由 + 精确版本 + 构建/运行命令 + 依赖红线，写入《项目事实文件》。

## 执行步骤

### 1. 按约束选型（决策维度）
- **项目类型**：Web 应用 / 内部工具 / API 服务 / 移动 / 数据系统 / 桌面，各有主流栈。
- **团队熟悉度**：优先团队已经会的技术，学习成本 > 技术先进性。
- **约束条件**：部署环境、性能要求、合规、预算、已有系统对接。
- **生态与维护**：选社区活跃、文档完善、长期维护的成熟技术，避免冷门/停更项目。
- **原则**：够用即可，不过度选型；无聊的成熟技术优于 exciting 的新技术。

### 2. 分层选型清单
逐层确定并说明理由：
- 语言与运行时
- 前端框架 / UI 方案 / 样式方案 / 图标
- 后端框架 / API 风格（REST/GraphQL/RPC）
- 数据库 / ORM 或数据访问层 / 缓存
- 认证鉴权方案
- 构建工具 / 包管理器 / 运行环境版本
- 部署与进程管理方式

### 3. 版本锁定（关键纪律）
- **精确记录每个依赖的版本号**（区分 `^`/`~`/精确锁定）。关键框架建议锁死。
- 记录运行时版本要求（如 Node/Python/Go 版本）。
- **红线**：大版本常有破坏性变更。写任何框架代码前，先读该版本的官方文档（本地 `node_modules` 或官网），**不要凭记忆**——API 可能已变。

### 4. 依赖红线
- 明确禁止引入的东西（如为保持轻量禁止重型 UI 库、禁止重复功能的库）。
- 新增依赖前评估：是否必要？维护状态？体积？是否与现有栈冲突？
- 依赖越少越好，每加一个都是长期维护负担。

### 5. 构建/运行约定
- 固化 install / build / dev / test / start 命令。
- 记录环境特殊性（如特定构建标志、镜像源、环境变量、Node 版本切换）。

## 交接
- → devflow-database：选定的 ORM/数据库约束 schema 设计。
- → devflow-frontend-dev / devflow-backend-dev：清单是它们的技术前提。
- → devflow-deployment：构建/运行约定是部署基础。
- 上游依赖 devflow-architecture 的分层与选型原则。

## 关键陷阱
- 凭记忆写框架 API（不看当前版本文档）→ 用了废弃写法，构建/运行报错。
- 版本不锁定 → 不同环境装出不同版本，"我这能跑你那不行"。
- 追新选不成熟技术 → 踩坑无社区支持。
- 过度引入依赖 → 体积大、冲突多、维护重。

## 验证
- 清单覆盖各层，每项有版本号与选型理由。
- 干净环境按约定命令能一次装好、构建、运行。
- 依赖红线明确记录，无冗余依赖。
