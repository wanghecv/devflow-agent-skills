# devflow · 通用软件交付方法论总控

这是一套**技术栈无关、业务无关**的软件交付方法论，覆盖从模糊想法到正式交付的完整链路。它不替你选框架、不假设你的业务，而是给你一条"该按什么顺序做、每步产出什么、怎么交接、怎么验证"的标准管线。任何 AI（Qoder / Codex / Claude 等）或工程师装上这套 skill 组，都能按统一节奏推进项目。

> 与 `collabflow` 的关系：`collabflow` 是 devflow 在"派单/协同/流程管理"类系统上的一个**具体落地实例**（绑定了 Next.js/Prisma/朗科数智协同等具体选型）。要做通用项目用 devflow；要做同类协同系统可直接参考 collabflow。

## 何时使用
- 从零构建任意软件系统
- 对既有项目做规范化二次开发
- 团队/多 AI 协作需要统一开发节奏与产出标准
- 用户说"按方法论来""走标准流程""规范化开发"

## 黄金法则：先对话，后执行
**任何开发动作之前，必须先完成需求对话（devflow-requirements）并形成书面结论。** 不允许跳过对话直接写代码。需求不清时，宁可多问，不可臆测。

## 全流程管线（按序调用子 skill）

| 阶段 | 子 skill | 产出物 |
|---|---|---|
| 0 对话 | `devflow-requirements` | 需求结论纪要 |
| 1 需求 | `devflow-prd` | PRD 需求文档 |
| 2 产品 | `devflow-product-definition` | 角色/模块/功能矩阵 |
| 3 架构 | `devflow-architecture` | 架构方案 + 目录结构 |
| 4 原型 | `devflow-prototype` | 页面原型/线框 |
| 5 设计 | `devflow-design-style` | 设计语言 + 美术规范 |
| 6 技术栈 | `devflow-tech-stack` | 技术选型 + 版本锁定 |
| 7 规范 | `devflow-code-conventions` | 代码风格/检查/循环约束 |
| 8 前端 | `devflow-frontend-dev` | 页面 + 组件 |
| 9 后端 | `devflow-backend-dev` | API + 业务逻辑 |
| 10 数据库 | `devflow-database` | 数据模型 + 变更 SOP |
| 11 测试 | `devflow-testing` | 测试点 + 冒烟 + 指标验证 |
| 12 部署 | `devflow-deployment` | 部署 + 运维 |
| 13 文档 | `devflow-docs` | 交付文档 |

> 阶段可合理并行：PRD 确定后，产品定义/架构/原型/设计/技术栈/数据库可并行；技术栈与规范确定后，前后端可并行。

## 全局工程纪律（所有子 skill 共同遵守）
- **文档先行**：每阶段有明确产出物，经确认再进入下一阶段。
- **事实与约定落盘**：项目的具体选型、版本、路径、约定统一记进一份《项目事实文件》（如 `DEVELOPMENT_GUIDE.md` / `AGENTS.md`），skill 只讲方法，不硬编码项目细节。
- **依赖方向单一**：分层清晰，禁止循环依赖，上层可依赖下层、反之不可。
- **边界即校验**：所有外部输入在入口校验；所有受保护操作先鉴权。
- **写操作要原子**：多步数据变更用事务，失败可回滚。
- **可追溯**：关键状态变更留痕，便于审计与排障。
- **不臆造**：未知信息用 `XXX` 占位或询问，绝不编造版本/接口/数据。

## 执行步骤
1. **识别项目类型与现状**：新建还是二次开发？已存在代码就先读项目事实文件与目录结构。
2. **强制对话**：调用 `devflow-requirements` 澄清目标、范围、约束、验收标准，形成结论。
3. **按管线推进**：依序（或合理并行）调用各阶段子 skill，每阶段产出确认后再继续。
4. **全程守纪**：遵守上述全局工程纪律与项目事实文件中的具体约定。
5. **交付收尾**：测试 → 冒烟 → 部署 → 文档。

## 关键陷阱
- 跳过需求对话直接写代码（违反黄金法则）
- 把具体技术栈/版本写死进通用流程（应落项目事实文件）
- 阶段产出未确认就往下冲，返工成本高
- 臆造接口/版本/数据而非询问或占位

## 验证
每阶段自检：产出物是否齐全、是否符合全局纪律、是否经确认？最终系统须通过 `devflow-testing` 的核心测试点与冒烟。
