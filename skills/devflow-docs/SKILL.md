# devflow 交付文档产出

## 定位
项目收尾要交付一整套正式文档。本 skill 固化各类文档的结构、深度分级、排版规范和占位约定，保证不同 AI/人产出的文档风格统一、可直接交付。文档生成一律走 `docx` skill（Word）或相应格式 skill（PDF/Markdown）。

## 何时使用
- 交付前产出用户手册 / 技术文档 / 测试报告 / 验收报告 / 交接文档
- 需要把工程成果转成正式可交付文档
- 二次开发/维护文档（开发指导、架构说明）产出

## 产出物
一组正式文档（默认 `.docx`），排版规范、结构完整、未知信息 XXX 占位、生成后校验通过。

## 执行步骤

### 1. 文档类型与深度分级
先和用户确认要哪几类文档、各自深度，再动手。常见类型：
- **用户操作手册**：面向最终用户，按功能模块分章，步骤化"怎么操作、看到什么"。偏详细，配截图（截图暂缺用灰色占位框）。
- **技术/开发文档**：面向开发者与维护者。系统架构、模块划分、接口说明、数据模型、部署方式、二次开发指引。结构清晰、与代码一致。
- **测试报告**：围绕验收指标与关键功能，逐项用例-步骤-预期-实测-结论，多用表格。深度取决于验收要求。
- **验收/结题报告**：项目背景目标、建设内容、关键成果、测试与验收、试运行成效、效益分析、经验总结、附录。非常完整。
- **交接文档**：账号/环境/密钥位置、部署步骤、运维手册、已知问题与待办、联系人。
按用户诉求裁剪，不要一律全做。

### 2. 排版规范（强制，除非用户另有要求）
- 纸张 A4；正文统一字体（中文宋体、标题黑体；或英文 Arial），字号层级清晰。
- 表头统一底色（如浅蓝 `#D5E8F0`）。
- 含页眉、页脚（页码）、目录。
- 标题层级 H1/H2/H3 规范，段前段后间距统一。
- 图表编号、题注规范；引用来源标注。

### 3. 占位约定
- 未知/待补信息一律用 `XXX` 占位（如具体人名、日期、单位抬头、实测数值、基线）。
- 截图暂缺用灰色占位框，标注"[截图：XXX 页面]"。
- 先把内容结构搞完整，占位处交由用户后续补充。绝不瞎编事实性数据。

### 4. 内容来源对齐（关键）
- 文档描述必须与实际代码/系统一致：写关键技术、指标、功能前，用代码或运行证据核对，不夸大不虚构。
- 项目名称、术语、系统命名全文统一（大小写、中英文一致）。
- 技术栈版本、部署方式引用 devflow-tech-stack / devflow-deployment 沉淀的事实或《项目事实文件》。
- 指标类结论引用 devflow-testing 的实测结果，未实测的标 XXX。

### 5. 生成与校验
- 调 `docx` skill（或 pdf/markdown skill）生成文档。
- 生成后校验文件完整、可打开（docx 用 `unzip -t`）。
- 输出到用户可见的 outputs 目录，用 file:// 链接分享，附一句内容概述即可，不长篇复述文档内容。

### 6. 常见写入陷阱
- 用 JS/文档库拼内容时，中文双引号 “ ” 直接写进 JS 源码字符串会被解析器当界定符导致 SyntaxError，需用 `\u201c` / `\u201d` 转义。
- 长文档分章生成再合并，避免一次性拼接出错难定位。

## 交接
- 上游依赖 devflow-testing（测试结论）、devflow-architecture（架构描述）、devflow-tech-stack（版本事实）、devflow-deployment（部署事实）。
- 是整套方法论的收尾交付环节。

## 关键陷阱
- 文档吹嘘与代码不符 → 交付被质疑，先核对证据。
- 排版不统一（无页眉页脚/目录、表头无色、字体混乱）→ 不专业。
- 中文引号写入 JS 源码 → SyntaxError，用 unicode 转义。
- 项目名/术语全文混用 → 交付前统一。
- 未知信息留空或瞎编 → 一律用 XXX 占位。
- 不问需求就全类型都写 → 先确认要哪几类、各自深度。

## 验证
- 每个文档生成后校验通过、能打开。
- 章节数与深度分级匹配，排版规范齐全（A4/统一字体/表头底色/页眉页脚/目录）。
- 关键技术与指标描述与代码/实测一致，占位处均为 XXX，命名术语全文统一。
