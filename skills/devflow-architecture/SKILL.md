# devflow 系统架构设计

## 定位
把产品定义转化为技术骨架：怎么分层、模块怎么组织、目录怎么摆、依赖往哪个方向流、关键横切能力（认证/日志/错误/配置）放哪。好的架构让后续开发"知道每行代码该放哪"，也让系统可维护、可扩展、可测试。

## 何时使用
- PRD/产品定义确定后搭骨架
- 二次开发前理清现有架构
- 需要做重大架构决策或重构

## 产出物
架构方案（分层图 + 说明）、目录结构、核心模块设计、架构决策记录（ADR）。

## 执行步骤

### 1. 选择架构风格（按项目类型）
- 中小型 Web/内部工具：**分层架构**（表现层 → 应用/API 层 → 领域/业务层 → 数据访问层 → 存储）足够，别过度设计。
- 复杂业务：考虑模块化单体（modular monolith）按领域分模块，优于过早上微服务。
- 微服务只在有明确独立部署/团队/扩展诉求时才用，否则是负担。
- 原则：**从简单开始，为演进留缝**，不要为想象中的规模买单。

### 2. 定义分层与依赖方向（核心纪律）
- 明确每一层职责，规定依赖只能自上而下单向流动，**禁止循环依赖**。
- 表现层（页面/组件）只调用应用层接口，**绝不直接访问数据库**。
- 业务逻辑集中在领域/业务层，不散落在路由或页面里。
- 数据访问统一收口（ORM/Repository），上层不写裸 SQL。

### 3. 设计目录结构
- 按层 + 按领域组织，命名一致、可预测。
- 明确各类文件归属：页面/路由、组件、业务逻辑、数据访问、工具、配置、类型。
- 让人"看路径就知道职责"。

### 4. 横切能力设计
- **认证与鉴权**：统一中间件/守卫，权限校验前置。
- **错误处理**：统一错误结构与分层传播策略。
- **日志与审计**：关键操作留痕，日志分级。
- **配置管理**：环境变量/配置中心，敏感信息不落代码。
- **事务与一致性**：跨表写操作的事务边界。

### 5. 核心模块设计
- 针对本项目最复杂/最有价值的模块（如流程引擎、计费、推荐、权限）画内部结构与接口。
- 定义模块对外契约，隐藏内部实现。

### 6. 架构决策记录（ADR）
- 每个重要决策记：背景、可选方案、取舍理由、结论。便于后人（含 AI）理解"为什么这么设计"。

## 交接
- → devflow-tech-stack：架构风格约束具体选型。
- → devflow-database：领域模型映射数据模型。
- → devflow-backend-dev / devflow-frontend-dev：分层与目录是编码骨架。
- 上游依赖 devflow-product-definition。

## 关键陷阱
- 过度设计（小项目上微服务/复杂 DDD）→ 维护成本爆炸。
- 依赖方向混乱、页面直连数据库 → 耦合、难测、泄露。
- 横切能力（鉴权/日志/错误）不统一 → 到处重复、漏洞百出。
- 不写 ADR → 后人看不懂设计意图，乱改。

## 验证
- 分层清晰、依赖单向、无循环依赖。
- 目录结构可预测，各类文件有明确归属。
- 横切能力有统一方案，核心模块有接口契约。
- 关键决策有 ADR 记录。
