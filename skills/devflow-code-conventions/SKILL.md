# devflow 代码风格与检查/循环约定

## 定位
这是"怎么写代码"的宪法。技术栈定了工具，本 skill 定规矩——命名、结构、校验、循环、错误处理、注释。目的是让任何接手者写出的代码与现有代码库无法区分，降低协作与维护成本。原则语言无关，具体规则落到项目所用语言。

## 何时使用
- 写任何代码前对齐规范
- Code Review 对照检查
- 新成员/新 AI 接手统一风格

## 产出物
一份《代码约束清单》，写入《项目事实文件》，作为强制规范。

## 执行步骤（约束维度）

### 1. 命名
- 统一大小写约定：变量/函数、类型/类、常量、文件/目录各用一种风格并全局一致。
- 命名达意：布尔用 is/has/can 前缀；函数用动词开头；避免缩写和拼音。
- 同一概念全局同名词，不要一处 user 一处 account 混用。

### 2. 结构与组织
- 单一职责：一个文件/函数/类只做一件事。
- 遵循架构分层归属，代码放对目录（按 devflow-architecture）。
- 优先早返回（guard clause），减少嵌套层级（一般不超过 3 层）。
- 控制函数长度，过长就拆分；提取可复用逻辑，消除重复（DRY，但不过度抽象）。

### 3. 检查风格（校验）
- **边界处校验**：所有外部输入（请求体、参数、文件、用户输入）在入口立即校验，不合法立即返回错误，不带病往下走。
- **权限前置**：受保护操作先鉴权再执行，无权立即拒绝。
- **早失败**：前置条件不满足就提前 return/throw，避免深层嵌套 if。
- **契约清晰**：错误信息对用户友好、对开发可定位；不泄露内部细节/堆栈给外部。

### 4. 循环风格
- 纯数据转换优先用函数式（map/filter/reduce），意图清晰。
- 需要顺序等待的异步循环用 `for...of`（或语言对应的串行结构），**禁止在 forEach 里塞 async**（并发失控、无法等待）。
- 相互独立的异步任务批量执行用并发原语（如 Promise.all）；有依赖则串行。
- 循环外创建重资源（连接、客户端），不在循环内反复 new。
- 遍历大数据集前先分页/限定范围，避免全量加载。

### 5. 错误处理
- 不吞异常：禁止空 catch、禁止静默丢弃错误。
- 分层处理：底层抛出/记录，边界层转成统一错误响应。
- 多步写操作用事务，失败可回滚，保持一致性。
- 记录足够上下文（what/where/why）便于排障。

### 6. 注释与文档
- 注释解释"为什么"而非"是什么"（代码本身说明是什么）。
- 反直觉/破坏性/特殊约定处标注原因（如"红线：此表只增不改"）。
- 公共接口/复杂算法写文档注释。
- 保持注释与代码同步，过时注释比没注释更糟。

### 7. 一致性兜底
- 用 linter/formatter 自动化能自动的规则，人只 review 机器管不了的（命名、结构、职责）。
- 规范落进《项目事实文件》，团队共同遵守。

## 交接
- → devflow-frontend-dev / devflow-backend-dev：本清单是强制约束。
- → devflow-testing：检查风格决定测试断言点。
- 上游依赖 devflow-tech-stack（语言确定后规则具体化）。

## 关键陷阱
- 异步循环用 forEach+async → 竞态、无法等待、错误丢失。
- 边界不校验/权限不前置 → 脏数据、越权。
- 空 catch 吞错 → 线上问题无从定位。
- 命名不一致、概念多词 → 阅读成本高、误解。
- 过度抽象/过早优化 → 代码晦涩难维护。

## 验证
- lint/format 通过，无类型/静态检查错误。
- 抽查新代码符合命名、早返回、边界校验、事务、权限前置等硬性条款。
- 规范已落《项目事实文件》并被团队知晓。
