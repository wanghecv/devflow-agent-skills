# devflow PRD 需求文档

## 定位
把需求对话产出的《需求结论纪要》展开成一份正式、结构化、可评审、可作为开发依据的 PRD。PRD 是后续所有阶段（产品定义/架构/测试/验收）的共同基准，写清楚"做什么、为谁做、做到什么程度算完成"。

## 何时使用
- 需求对话完成，要落正式文档
- 需要与团队/客户对齐需求基线
- 二次开发前重建需求文档

## 产出物
一份完整 PRD（Markdown 或 Word）。

## 执行步骤

### 1. PRD 标准结构
1. **文档信息**：版本、作者、日期、状态、修订记录（未知用 XXX）。
2. **背景与问题**：为什么做、当前痛点、机会。
3. **目标与非目标**：明确要达成什么、这一期不做什么（防止范围蔓延）。
4. **目标用户与角色**：角色画像、各自诉求与权限差异。
5. **核心场景/用户故事**：以"作为 X，我想 Y，以便 Z"描述高频场景。
6. **功能需求清单**：编号、模块、功能描述、优先级（Must/Should/Could）、验收要点。
7. **业务流程说明**：关键流程的步骤/状态流转（文字或流程图）。
8. **非功能需求**：性能（响应时间/吞吐）、可用性、安全合规、可扩展性、兼容性、容量。量化指标必须可测。
9. **数据与集成**：涉及的数据实体、外部系统对接。
10. **验收标准**：整体怎样算完成，逐条可验证。
11. **未决问题/风险**：待确认项、假设、依赖与风险。

### 2. 写作要点
- 需求要**可验证**：避免"体验好""速度快"这类模糊词，改成"列表加载 P95 ≤ 1s"。
- 功能条目**原子化**：一条讲一件事，便于拆解和测试。
- 优先级明确：用 MoSCoW 或 RICE 辅助排序，MVP 边界清晰。
- 非功能需求单列一章，别埋在功能描述里。
- 未知信息一律 `XXX` 占位，不编造。

### 3. 评审闭环
产出后与需求方评审确认，记录修订。达成一致后冻结为基线，后续变更走变更流程。

## 交接
- → devflow-product-definition：功能清单细化为角色-权限矩阵与模块矩阵。
- → devflow-architecture：非功能需求（性能/扩展/安全）约束架构选型。
- → devflow-testing：验收标准与非功能指标是测试用例来源。
- 上游依赖 devflow-requirements 的结论纪要。

## 关键陷阱
- 需求不可验证 → 无法测试、无法验收。
- 漏写非目标 → 范围无限膨胀。
- 非功能需求缺失或模糊 → 架构无据可依、性能踩雷。
- 功能条目过大不原子 → 拆解和估时困难。
- 编造未知信息而非占位 → 基线失真。

## 验证
- 11 个结构章节齐全，功能有编号与优先级。
- 每条需求可验证，非功能指标量化。
- 需求方已评审确认，未决项已标注。
