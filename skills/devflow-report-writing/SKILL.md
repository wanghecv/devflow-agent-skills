# devflow 报告写作（行文逻辑与章节模板库）

## 定位
这是 `devflow-docs` 的深化配套。docs 负责"要交付哪些文档、排版规范、占位约定、生成校验"；本 skill 负责每类报告"具体怎么谋篇布局、每章写什么、行文逻辑主线怎么走"。写任何正式报告前，先在本 skill 找到对应类型的模板，按其骨架和逻辑组织内容，再用 `docx` skill 落地。

## 何时使用
- 撰写研发报告 / 开发报告 / 测试报告 / 试运行报告 / 结题报告 / 用户操作手册
- 已有零散内容，需要搭出专业、可直接交付的报告结构
- 评审/验收/对外交付前，需要统一报告的行文逻辑与深度

## 通用行文原则（所有报告共享）
1. **目的与读者先于结构**：先明确"这份报告给谁看、要支撑什么决策"，再搭章节骨架。不套模板套到内容与目的不符。
2. **证据/数据驱动**：每个结论都要有实测数据、代码事实或运行记录支撑。未实测的用 `XXX` 占位，绝不编造数值。
3. **深度分级**：同一类报告按用途调深浅（内部评审 < 正式验收 < 对外交付/存档）。
4. **金字塔表达**：结论先行，或每章"总—分—总"，先给判断再给依据。
5. **口径一致**：项目名、术语、指标口径、单位、版本号全文统一，且与真实系统一致。
6. **可读性**：对比/清单/实测数据一律用表格承载；关键结论加粗或独立成段；图表编号带题注。

## 报告类型模板

### A. 研发报告 / 开发报告
**读者与用途**：科技项目主管、研发管理层、评审专家；用于立项验收、研发过程归档、高新/加计扣除等。
**深度**：中—高，技术与创新并重。
**章节大纲（逐章写什么）**：
1. 立项背景与意义——行业/业务痛点、为什么值得做、预期价值。
2. 研发目标与考核指标——总体目标 + 可量化考核指标（性能/功能/效益，明确达标线）。
3. 研发内容与技术路线——做什么、分几个方向、整体技术路线与方法（可配路线图）。
4. 关键技术与创新点——逐项关键技术，说明原理、难点、创新之处。
5. 研发过程与阶段成果——按阶段/里程碑叙述推进过程与各阶段产出。
6. 测试与验证——如何验证是否达到考核指标，附核心实测结果。
7. 效益分析——直接效益（效率/成本）+ 间接效益（管理/推广）。
8. 结论与后续——达成情况判定 + 不足 + 后续规划。
   附录：术语、指标口径、数据表、知识产权/软著情况。
**行文逻辑主线**：为什么做 → 定成什么目标 → 怎么做（技术路线）→ 做出了什么（阶段成果+创新）→ 验证是否达标 → 值不值（效益）→ 结论。
**研发报告 vs 开发报告**：研发报告偏立项意义、创新性、技术路线、知识产权（对外/科技项目口径）；开发报告偏工程实现、模块开发、进度与质量（对内研发管理口径）。二者骨架相通，按需增减"创新性/知识产权"或"进度/质量"章节。

### B. 测试报告（技术要求测试报告）
**读者与用途**：验收方、测试评审、甲方；用于证明系统达到约定技术要求/验收指标。
**深度**：高，以数据说话。
**章节大纲**：
1. 测试概述——测试背景 / 目的 / 范围 / 依据（标准或合同指标）/ 测试环境。
2. 测试方法与工具——各类测试（性能/压力/功能/效率对比）的方法与所用工具。
3..N. **按"技术要求/验收指标"逐项分章**，每项指标独立成章，章内走**四段式**：
   - 测试项说明（这项指标要求什么、如何判定达标）
   - 测试用例设计（用例表：编号/场景/步骤/预期）
   - 测试结果（实测数据表：预期 vs 实测）
   - 测试结论（是否达标，一句话判定）
   末章. 测试总结——指标达标情况汇总表 / 遗留问题与建议 / 最终结论。
   附录：测试用例完整清单 / 原始数据记录说明。
**行文逻辑核心**：**以验收指标为章节骨架**，一项指标一章，章内四段式，用实测数据表证明达标；总结章回收所有指标给汇总判定。指标复杂时可在章内再分子场景（H3）。
**常用表格**：用例表、预期-实测对照表、指标达标汇总表、性能数据表（P50/P95/P99 或分档）。

### C. 试运行报告
**读者与用途**：项目管理方、验收方；证明系统在真实环境稳定运行、达到试运行目标。
**深度**：中，重"真实运行"。
**章节大纲**：
1. 项目背景——简述系统与试运行缘由。
2. 试运行环境——硬件 / 软件（含版本）/ 网络 / 系统部署架构，**写全写实**。
3. 试运行范围与计划——周期 / 范围 / 参与人员（角色）/ 试运行目标。
4. 试运行内容与结果——按功能模块逐项记录真实运行情况与结果。
5. 问题与解决——问题清单 → 处理措施 → 当前状态（闭环）。
6. 系统性能评估——响应时间 / 并发能力 / 稳定性 / 数据完整性，**带真实实测表**。
7. 试运行结论——总体评价 / 目标达成情况 / 遗留问题与改进建议。
**行文逻辑**：以"真实运行"为核心——环境写实、过程写实、性能用实测数据、问题如实记录并闭环，结论回到"试运行目标是否达成"。

### D. 结题报告
**读者与用途**：验收委员会、出资方、存档；项目全周期总结，**最完整的一类**。
**深度**：非常高。
**章节大纲**：
1. 项目概述——背景 / 目标 / 范围 / 组织 / 周期。
2. 项目完成情况——计划完成情况 / 功能交付清单 / 里程碑回顾 / 预算执行情况。
3. 技术方案与实现——总体架构设计 + **每项关键技术展开到子模块/算法级** + 数据库（数据模型）设计。
4. 关键技术与创新——技术创新点总结 / 技术难点与解决方案 / 知识产权情况。
5. 项目成果与效益——直接成果 / 效率提升 / 管理价值 / 推广前景（带数据）。
6. 项目管理回顾——需求管理 / 质量管理 / 风险管理 / 沟通协作。
7. 经验总结与改进建议——成功经验 / 不足与教训 / 改进建议 / 后续规划。
8. 结论。
   附录：系统截图清单 / 测试用例汇总 / 参考文献。
**行文逻辑**：以"项目全生命周期"为轴——为什么立项 → 做成了什么 → 怎么做的（技术实现，展开最深）→ 有何创新 → 产生什么效益 → 管理与经验 → 结论收口。**技术实现章是重心**，每项关键技术展开到子模块/算法级并用代码事实支撑，不泛泛而谈。

### E. 用户操作手册
**读者与用途**：最终用户（多为非技术）；教用户会用系统。
**深度**：详细、步骤化、少术语。
**章节大纲**：
1. 系统概述——系统简介 / 运行环境 / 角色说明。
2. 登录——登录操作 / 修改密码 / 安全说明。
3..N. **按功能模块逐章**，每章步骤化：怎么进入 → 怎么操作 → 看到什么 → 注意事项；关键步骤配截图。
   系统设置章——各类配置项操作。
   常见问题 FAQ——Q&A 形式，覆盖高频问题与故障自助排查。
**行文逻辑**：面向最终用户，按"用户实际使用顺序 / 功能模块"组织；动词开头的步骤化描述；少术语、多截图；末尾用 FAQ 兜底常见困惑。

## 排版规范（强制，与 devflow-docs 一致）
A4；正文统一字体（中文宋体、标题黑体，或英文 Arial）；表头统一底色（如浅蓝 `#D5E8F0`）；含页眉、页脚（页码）、目录；标题层级 H1/H2/H3 规范；图表编号带题注；段前段后间距统一。

## 占位约定
未知/待补信息一律 `XXX`；截图暂缺用灰色占位框并标注"[截图：XXX]"；实测数据未测标 `XXX`，绝不编造。

## 交接
- **上游依赖**：devflow-testing（实测数据/测试结论）、devflow-architecture（架构描述）、devflow-tech-stack（版本事实）、devflow-deployment（环境/部署事实）、devflow-product-definition（角色/功能模块）。
- **落地**：调 `docx` skill 生成 `.docx`，生成后 `unzip -t` 校验，输出到 outputs 用 file:// 分享。
- **配套**：与 `devflow-docs` 配合使用——docs 管"交付哪些+排版+占位+校验"，本 skill 管"每类报告怎么写"。

## 关键陷阱
- 套模板套到内容与目的不符 → 先定目的与读者，再搭骨架。
- 结论无数据支撑 / 编造实测值 → 用真实数据，未测标 XXX。
- 结题报告技术章写太浅（只罗列不展开）→ 关键技术必须展开到子模块/算法级。
- 测试报告不按指标分章、堆成一团 → 以验收指标为骨架，一项一章走四段式。
- 试运行报告环境/性能写实不足 → 环境写全含版本，性能配真实实测表。
- 操作手册术语多、无截图、无 FAQ → 面向小白，步骤化 + 配图 + FAQ 兜底。
- 各报告口径不一（项目名/指标/版本）→ 全文统一且与系统一致。

## 验证
- 报告章节与所选类型模板匹配，行文逻辑主线清晰、结论先行。
- 每个结论有数据/事实支撑，占位处均为 XXX。
- 排版规范齐全（A4/统一字体/表头底色/页眉页脚/目录/图表题注）。
- 命名与指标口径全文统一，docx 生成后校验通过、能打开。
