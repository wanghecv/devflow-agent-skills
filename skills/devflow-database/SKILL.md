# devflow 数据库设计与变更

## 定位
把产品定义中的角色、实体、状态机固化为数据模型，并规定一套"改 schema 不炸线上"的变更纪律。数据库是业务的地基，一旦设计不当或变更失控，代价极高。本 skill 语言/数据库无关，聚焦建模方法与变更纪律。

## 何时使用
- 新项目首次设计数据模型
- 新增功能需要加表/加字段
- 执行 schema 变更、迁移
- 排查数据层错误

## 产出物
数据模型设计（实体/字段/关系/枚举/索引）+ schema 变更 SOP，落到项目所用 ORM/DDL。

## 执行步骤

### 1. 从领域模型到数据模型
- 从 PRD/产品定义识别核心实体（名词）与关系（一对一/一对多/多对多）。
- 每个实体定字段、类型、约束（非空/唯一/默认值/长度）。
- 把业务状态固化为枚举，避免用魔法字符串。
- 多对多用关联表；外键明确级联策略。

### 2. 建模原则
- **范式与反范式权衡**：默认规范化减少冗余；有明确性能诉求时局部反范式并说明理由。
- **索引**：为高频查询条件、外键、排序字段建索引；不滥用（写放大）。
- **主键策略**：统一（自增/UUID/雪花），考虑分布式与暴露风险。
- **时间字段**：多数表带 createdAt/updatedAt；软删除按需。
- **审计/留痕表**：需要不可篡改日志时，设计 append-only 表——**只有创建时间、没有更新时间、只增不改不删**，这是审计的物理保证。

### 3. schema 变更 SOP（关键纪律）
1. 改 schema 定义（ORM schema / DDL）。
2. 生成类型/客户端（若用带代码生成的 ORM，如 Prisma）——让 TS/代码类型与新 schema 同步。
3. 应用变更到数据库（migrate / db push）。**红线**：只生成类型不建表 → 运行报"表不存在"；只建表不生成类型 → 构建期类型错误。两步都要做。
4. 本地验证后再上生产。
5. **生产变更顺序**：先备份 → 生成/迁移 → 再构建部署。破坏性变更（删列/改类型）要分步、可回滚，避免直接丢数据。
6. 迁移脚本纳入版本控制，可重放。

### 4. 数据访问约定
- 数据访问统一收口（ORM/Repository 层），上层不写裸 SQL（除非有明确的性能优化且封装好）。
- 多步写操作用事务，保证一致性。
- 查询先限定范围/分页，避免全表扫描。
- 敏感字段（密码等）加密/哈希存储，绝不明文。

### 5. 种子与初始化
- 提供 seed 脚本初始化基础数据（角色、配置、管理员账号）。
- seed 依赖表已建好，故 SOP 中"建表"必须在"seed"之前。

## 关键陷阱
- 只生成类型不建表（或反之）→ 构建报错或运行"表不存在"。
- 生产直接跑破坏性迁移不备份 → 数据丢失不可逆。
- 状态用魔法字符串不用枚举 → 脏数据、难维护。
- 给审计表加可更新字段 → 破坏不可篡改性。
- 缺索引 → 数据量上来后查询雪崩。

## 验证
- 模型覆盖全部核心实体与关系，字段约束完整。
- 变更 SOP 走通：改 schema → 生成 → 迁移 → seed 全流程无错。
- 高频查询有索引；审计表 append-only；敏感字段加密。
