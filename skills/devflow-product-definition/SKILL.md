# devflow 产品定义

## 定位
把 PRD 的"功能需求清单"翻译成产品可落地的结构：谁（角色）能在哪（模块/页面）做什么（功能/权限），按什么规则（业务流程/状态机）流转。这是连接"需求"与"架构/开发"的桥梁，也是权限体系和信息架构的源头。

## 何时使用
- PRD 确定后要细化产品结构
- 需要设计角色权限体系
- 需要梳理模块划分、页面清单、状态流转规则

## 产出物
角色-权限矩阵、功能模块清单、页面/路由清单、业务与状态规则定义。

## 执行步骤

### 1. 角色建模
- 列出所有角色（含管理员/普通用户/访客/审计等）。
- 每个角色写清：核心诉求、典型操作、数据可见范围。
- 识别角色间的层级与互斥关系。

### 2. 功能模块划分
- 按领域把功能聚合成模块（如 用户管理 / 业务核心 / 报表 / 系统设置）。
- 每个模块列子功能，标注优先级与所属迭代。
- 模块边界清晰，高内聚低耦合，为架构分层做准备。

### 3. 角色-权限矩阵（核心产出）
- 二维矩阵：行=角色，列=功能/资源操作（查看/创建/编辑/删除/审批/导出…）。
- 每格标 allow / deny / 条件（如"仅本人""仅本部门"）。
- 明确权限维度（功能级、数据级、字段级、操作级），为后端鉴权提供依据。

### 4. 页面/路由清单
- 列出所有页面及其路由、归属模块、可访问角色。
- 标注页面类型（列表/详情/表单/看板/设置）。

### 5. 业务与状态规则
- 定义核心实体的状态机（状态集合 + 合法流转 + 触发动作 + 流转后副作用）。
- 写清业务规则（约束、校验、计算口径、审批规则）。
- 如涉及流程/审批，明确串行/并行/会签等模式。

## 交接
- → devflow-architecture：模块划分与权限维度决定分层与鉴权设计。
- → devflow-prototype：页面清单是原型蓝图。
- → devflow-database：角色、实体、状态机映射为数据模型。
- → devflow-backend-dev：权限矩阵与状态规则是鉴权和业务逻辑依据。
- 上游依赖 devflow-prd。

## 关键陷阱
- 权限矩阵漏角色或漏操作维度 → 后期越权/补权限返工。
- 状态机漏非法流转定义 → 业务出现脏状态。
- 模块边界模糊 → 架构耦合、职责不清。
- 页面清单不定可访问角色 → 前端与鉴权对不上。

## 验证
- 角色、模块、页面、状态机四要素齐全。
- 权限矩阵每个角色×操作组合都有明确结论。
- 状态机每个状态都有进/出流转且无死锁。
