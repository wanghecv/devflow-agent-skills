# devflow 后端 API 与业务逻辑开发

## 定位
后端承载业务逻辑、数据一致性、认证鉴权与审计。全部在分层架构的中下层实现（API 层 → 业务/领域层 → 数据访问层），API 层薄、业务逻辑内聚、数据访问收口。本 skill 语言/框架无关，聚焦通用工程要点。

## 何时使用
- 新增/修改任意 API 接口
- 实现认证鉴权、业务规则、事务、数据聚合
- 对接外部系统
- 排查鉴权/一致性/性能问题

## 产出物
API 接口 + 业务逻辑 + 数据访问，通过构建、lint，契约与前端对齐。

## 执行步骤

### 1. API 层规范
- 按资源设计路由，语义化 HTTP 方法（GET 查/POST 增/PATCH 改/DELETE 删）或统一的 RPC 风格，全局一致。
- 统一响应结构：成功返回数据体，失败返回统一错误结构 `{ error/code/message }` + 合适状态码（400 参数错/401 未认证/403 越权/404 不存在/409 冲突/500 服务端错）。
- API 层保持"薄"：只做输入校验、鉴权、调用业务层、组装响应，不堆业务逻辑。
- 版本化 API（如 /v1/）以便演进。

### 2. 认证与鉴权（通用 RBAC）
- 认证：签发/校验令牌（如 JWT），从请求解析当前用户身份。密码等凭据哈希存储，绝不明文；敏感传输加密。
- **权限前置**：受保护接口第一步鉴权——取当前用户 → 校验角色/权限（对照 devflow-product-definition 的权限矩阵）→ 无权立即 403，再谈业务。
- 权限校验收敛到统一中间件/守卫/工具函数，不在每个接口重复散落实现。
- 数据级权限（本人/本部门/全部）在查询层过滤，不只靠前端隐藏按钮。

### 3. 业务逻辑层
- 业务规则集中在领域/业务层，可独立测试，不依赖具体 HTTP 框架。
- 复杂状态流转用状态机实现：校验流转合法性（非法流转拒绝）→ 执行副作用 → 记录留痕。
- 流程/审批类系统：把流程引擎抽成独立模块，对外暴露清晰契约，内部隐藏实现（串行/并行/会签等模式可配置）。

### 4. 事务与一致性
- 跨多表/多步的写操作必须用事务包裹，保证原子性——要么全成功要么全回滚。
- 典型场景：状态变更 + 留痕 + 关联更新，必须同一事务，禁止拆开写。
- 并发写注意竞态，用事务隔离/乐观锁/幂等键防范。

### 5. 审计与留痕
- 关键操作写审计日志/留痕表（append-only，只增不改）。
- 记录 who/when/what/before-after，便于追溯与合规。

### 6. 数据聚合与外部集成
- 聚合/统计逻辑收在业务层，页面/API 调用；查询先限定范围/分页再聚合，避免全表扫描。
- 外部集成：配置（endpoint/key）从配置/密钥管理读取不硬编码；调用设超时与重试；失败降级或明确报错；注意限流与幂等。

### 7. 错误处理与安全
- try/catch 包裹业务，catch 记录上下文并返回统一错误结构，不吐堆栈给外部。
- 防注入（参数化查询）、防越权、防 XSS/CSRF、校验所有输入、敏感信息脱敏。

## 交接
- → devflow-testing：API 契约、权限矩阵、事务原子性、状态机是测试重点。
- → devflow-frontend-dev：约定请求/响应结构。
- 上游依赖 devflow-database / devflow-code-conventions / devflow-architecture / devflow-product-definition。

## 关键陷阱
- API 层塞满业务逻辑 → 难测、难复用。
- 忘记权限前置或只做前端隐藏 → 越权访问。
- 状态变更与留痕分两次写、不用事务 → 中途失败数据不一致。
- 凭记忆写框架 API（如异步 params 需 await）→ 运行报错。
- 密钥硬编码、外部调用无超时 → 泄露、雪崩。

## 验证
- 构建 + lint 通过。
- 手测：正常(200)/未认证(401)/越权(403)/非法输入(400)/非法流转(拒绝)/事务回滚 均符合预期。
- 每次关键操作留痕有且仅有一条对应记录；聚合结果准确。
